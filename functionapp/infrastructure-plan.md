# Private Azure Function App infrastructure plan

**Status:** Design and deployment artifacts; no Azure resources have been created.

## Goal

Deploy a Linux Azure Function App with private inbound access, regional outbound VNet integration, and a private Storage account for Functions host state and content. The deployment uses Functions runtime v4, Python 3.12 by default, and an Elastic Premium plan (EP1 by default).

## Architecture

- One VNet with dedicated subnets for regional App Service/Functions VNet integration and private endpoints. The integration subnet is delegated to `Microsoft.Web/serverFarms`; the private endpoint subnet is separate and has private endpoint network policies disabled.
- A Linux Elastic Premium Function App with HTTPS-only access and `publicNetworkAccess` disabled. A `sites` private endpoint and `privatelink.azurewebsites.net` private DNS zone provide private inbound resolution.
- A StorageV2 account with public network access disabled. Private endpoints and linked private DNS zones are created for Blob, File, Queue, and Table services; the Function App connects to its host storage and Azure Files content share over the VNet.
- `WEBSITE_CONTENTOVERVNET=1` enables the Functions app to reach its Azure Files content share through VNet integration. The app uses Functions host v4.

The template provisions infrastructure only; it does not publish function code or create function triggers. The Function App name and Storage account name must be globally unique. The template uses a Storage account key for the host and content connection settings; the key is generated by ARM and is not an output or a script parameter.

## Example network ranges

| Network | Example prefix |
|---|---|
| VNet | `10.50.0.0/16` |
| Functions integration subnet | `10.50.1.0/26` |
| Private endpoint subnet | `10.50.2.0/24` |

These are illustrative only. Confirm that ranges do not overlap connected VNets, peering, VPN, or on-premises networks. Size the private endpoint subnet for the Function App and four Storage private endpoints.

## Deployment and validation

From the repository root, use `./functionapp/deploy.sh --mock` to compile/preview without Azure deployment calls, or `./functionapp/deploy.sh` to deploy interactively. Parameter files in `input/functionapp/` are auto-discovered and processed without prompts; review them before a live deployment. Use `--interactive` to bypass discovery. Defaults are only accepted when `--use-defaults` is explicitly supplied.

After deployment, validate that the Function App hostname resolves to a private endpoint address from the linked VNet, that Storage service names resolve to their private endpoint addresses, and that HTTPS access works from intended private clients. Confirm that public ingress and Storage public access are disabled. Function code and triggers must be deployed separately.

## Constraints and costs

Elastic Premium and private endpoints incur ongoing charges. EP1 is an example, not a workload sizing recommendation; verify regional availability, quotas, scale needs, and expected costs before deploying. Storage and private DNS zones are deployed into the same resource group and are removed by the cleanup script.
